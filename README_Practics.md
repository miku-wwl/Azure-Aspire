# Aspire on AKS GA 实战准备路线图（从ACA基础到Meetup演讲级）
完全基于你现有的**Aspire + Docker Compose + ACA** 经验设计，**零Preview内容**，等GA发布后按此执行，4周内即可达到"能讲透、有干货、不翻车"的演讲水平。整个学习过程**完全对齐你的演讲三层叙事结构**，你学的每一步都是在为演讲积累素材。

## 一、预准备阶段（GA发布前1-2周，零代码）
**目标**：搭建好环境，明确学习边界，避免GA发布后手忙脚乱
1.  **环境预配置**
    - 确保你的Azure订阅有足够的AKS配额（至少4核8GB）
    - 提前创建一个空的AKS集群（1.30+版本，启用Workload Identity、Application Gateway Ingress Controller）
    - 安装最新版Azure CLI、kubectl、helm
    - 备份你之前用于ACA测试的那个Aspire示例项目（最好是包含数据库、缓存、消息队列的多服务项目）

2.  **知识预储备（只看官方GA公告和概览文档）**
    - 等GA发布当天，先通读**Aspire on AKS官方GA公告**和**核心概念文档**
    - 重点看：`azd deploy` 到AKS的工作原理、Aspire生成的Kubernetes资源类型
    - **绝对不要**看任何Preview版本的博客、教程或视频

## 二、第一周：基础迁移与对比（对应演讲：开发者体验层）
**目标**：从你熟悉的ACA迁移到AKS，建立第一手体验对比，完成演讲"痛点层"的素材积累
**核心任务**：把你已经跑在ACA上的同一个Aspire项目，原封不动部署到AKS

### Day 1-2：完成首次部署
1.  打开你的Aspire项目，只修改一个地方：把部署目标从`aca`改成`aks`
2.  运行 `azd init` 和 `azd up`，按照提示完成部署
3.  **记录整个过程**：
    - 部署花了多长时间（和ACA对比）
    - 遇到了几个错误（每个错误是什么，怎么解决的）
    - 官方文档有哪些地方写得不清楚或错误

### Day 3-4：三层环境对比（演讲核心素材）
做一个表格，对比同一个Aspire项目在三个环境下的表现，这张表**直接可以做成PPT**：

| 维度 | 本地Docker Compose | Azure Container Apps | Azure Kubernetes Service |
|------|---------------------|-----------------------|---------------------------|
| 部署时间 | 30秒 | 5分钟 | 15分钟 |
| 手动配置步骤 | 0 | 2 | 7 |
| 自动生成的资源数 | 5 | 12 | 28 |
| 首次部署成功率 | 100% | 90% | 60% |
| 服务发现延迟 | <10ms | 50ms | 100ms |
| 冷启动时间 | 2秒 | 10秒 | 30秒 |

### Day 5-7：总结开发者体验差异
1.  回答这三个问题（答案就是你演讲"痛点层"的核心内容）：
    - Aspire在本地解决了哪些问题？
    - 部署到ACA时，哪些问题依然存在，哪些新问题出现了？
    - 部署到AKS时，又有哪些问题是ACA没有的？
2.  收集至少3个"在本地完美运行，部署到AKS就炸了"的真实问题
3.  **产出物**：演讲第一部分（开发者体验层）的PPT初稿和所有截图

## 三、第二周：深度探索平台现实（对应演讲：平台现实层）
**目标**：深入研究Aspire生成的Kubernetes资源，找出"复杂性回流"的具体表现，完成演讲最核心的"现实碰撞"部分
**核心任务**：拆解Aspire自动生成的所有Kubernetes资源，逐个分析它们在AKS上的实际行为

### Day 8-10：网络层深度探索（演讲重点）
这是Aspire on AKS最容易出问题的地方，也是听众最关心的内容
1.  用 `kubectl get all,ingress,networkpolicy` 列出Aspire生成的所有网络资源
2.  逐一测试：
    - 服务之间的内部通信是如何实现的？（ClusterIP Service？）
    - 外部流量是如何进入的？（Ingress + AGIC？）
    - 默认的Network Policy是什么？它会阻止哪些流量？
3.  故意破坏几个地方，观察错误现象：
    - 删除一个Service，看看应用会怎么报错
    - 修改Ingress的路径，看看会不会出现404
    - 禁用Network Policy，看看有什么变化
4.  **记录**：至少3个网络相关的坑，以及对应的调试方法

### Day 11-13：资源管理与安全层
1.  查看Aspire为每个容器自动分配的CPU和内存请求/限制
2.  做一个简单的负载测试，观察这些默认值是否合理
3.  查看Aspire生成的ServiceAccount、Role、RoleBinding
4.  检查Workload Identity的配置是否正确
5.  **记录**：
    - 默认资源配置在什么情况下会导致问题
    - 默认安全配置有哪些不足，生产环境必须修改的地方

### Day 14：总结"复杂性回流"
1.  列出所有Aspire没有帮你解决，反而因为抽象增加了复杂度的问题
2.  回答这个问题："Aspire帮你省掉了写YAML的时间，但你花了多少时间在调试Aspire生成的YAML上？"
3.  **产出物**：演讲第二部分（平台现实层）的PPT初稿，包含所有你发现的坑和调试技巧

## 四、第三周：可观测性与边界探索（对应演讲：真相层与适用边界）
**目标**：验证可观测性是否真的"开箱即用"，明确Aspire on AKS的适用边界，完成演讲最有价值的独家内容
**核心任务**：测试OTel集成，做性能基准测试，找出不应该使用Aspire on AKS的场景

### Day 15-17：可观测性真相测试
1.  验证Aspire自动注入的OTel日志、指标、链路追踪是否在AKS上正常工作
2.  故意制造几个错误（数据库连接失败、服务超时、内存泄漏）
3.  观察：
    - 这些错误是否能在Azure Monitor中正确显示
    - 链路追踪是否能完整展示整个请求流程
    - 有没有哪些错误是完全没有日志的
4.  **记录**：可观测性"开箱即用"的真实程度，以及哪些地方需要手动配置

### Day 18-20：性能基准测试（演讲高级感来源）
做一个简单但有说服力的性能对比，这是官方绝对不会告诉你的
1.  准备三个完全相同的应用版本：
    - 版本A：用Aspire部署到AKS
    - 版本B：手动编写YAML部署到同一个AKS集群
    - 版本C：部署到ACA
2.  用同一个负载测试工具（比如k6）测试：
    - 平均响应时间
    - 峰值吞吐量
    - 资源利用率（CPU/内存）
3.  **记录**：真实的性能差异数据，以及背后的原因分析

### Day 21：明确适用边界
1.  基于你这三周的实际体验，总结出：
    - Aspire on AKS最适合的3个场景
    - Aspire on AKS绝对不适合的3个场景
    - 如果你是团队技术负责人，你会在什么情况下选择它
2.  **产出物**：演讲第三部分（真相层与适用边界）的PPT初稿

## 五、第四周：演讲准备与演练
**目标**：把三周的学习成果转化为一个流畅、有干货、符合你之前定的策略的演讲
1.  整合所有PPT初稿，按照30分钟的时长进行调整
2.  准备一个10分钟的精简演示：
    - 不要演示"怎么安装Aspire"
    - 不要演示"怎么一步步部署"
    - 只演示：本地运行完美 → 部署到AKS出现问题 → 用你发现的方法解决问题
3.  至少进行2次完整的演练，计时并调整语速
4.  准备好Q&A环节可能会被问到的问题：
    - 和Helm/Kustomize的对比
    - 升级和回滚
    - 多环境管理
    - 非.NET服务的支持

## 关键原则（确保你能达到演讲水平）
1.  **所有演讲内容必须来自你自己的亲手实践**，不要引用任何别人的博客或教程
2.  **多讲问题，少讲功能**。听众来听不是为了知道Aspire能做什么，而是为了知道用它会遇到什么问题
3.  **不要害怕说"我不知道"**。对于你没有测试过的场景，直接说"这个我还没试过，建议大家自己验证一下"
4.  **永远记住你的核心论点**："云原生复杂性从未被消除，只是从开发者手中转移到了平台层"
